# Confidential swaps

Status: redesign in progress on the `confidential` branch. This changes parts of [protocol.md](protocol.md) and
[contracts.md](contracts.md), and replaces the Simplicity HTLC. Those documents still describe `main` until this lands.

Goal: **an outside observer can't link the two legs of a swap, and can't see the Liquid amount or asset.**

## What this hides

| Observer sees | Today | This design |
|---|---|---|
| Link between the Liquid and Solana legs | Public | Hidden |
| Liquid amount and asset | Public | Hidden |
| The Liquid output is a swap | Public | Hidden, unless it refunds |
| Solana escrow, addresses, amount, point `T` and revealed value | Public | **Still public**: USDT on Solana is transparent |
| Timing of the two legs | Public | Still public, and can suggest a link, above all for unusual amounts |
| L-BTC fee output | Public | Still public, as on every Liquid transaction |

The counterparty is not an outside observer. It sees both legs of its own swap.

## The construction

**Liquid.** A taproot output whose internal key is a MuSig2 aggregate of both parties' per-swap keys.

- *Claim:* a key-path signature, made with an adapter signature locked to a point `T`. On-chain it is one 65-byte witness item.
- *Refund:* a script-path spend of a Simplicity leaf: lock height, plus the sender's signature. It is the only path that needs one
  party alone, and using it reveals that the output was a timelocked swap.
- *Blinding:* the coin is sent to a confidential address. Its blinding key is generated by the taker and shared in the encrypted
  RFQ, so both parties can read the coin and nobody else can.

Elements tags its taproot hashes differently from Bitcoin (`TapTweak/elements`), so the tweak comes from rust-elements. The MuSig2
library's built-in taproot tweak would give a key no Liquid node accepts.

**Solana.** The escrow locks to the point `T` instead of a hash. A claim reveals `s = t·Gx mod n`, and the program checks it with
`sol_secp256k1_recover`: with hash 0, `r = Gx`, recovery id 0 and that `s`, recovery returns `t·G`. It costs about 25,000 compute
units, and needs no big-number code on-chain. Anyone then computes `t = s / Gx mod n` off-chain. This is why `T` and `t` are public on
Solana and yet give no link: nothing on Liquid contains `T`, and the adapter signature that relates them is held only by the parties.

## Flows

The taker makes the secret `t` and always locks first, as before. Both sides derive every address themselves.

### L-USDt → SOL-USDT

1. RFQ. The taker's accept carries `T`, its per-swap key and the blinding key. The terms carry the maker's per-swap key.
2. The taker pays the confidential address from any Liquid wallet.
3. The maker unblinds the coin, and checks asset and amount with enough confirmations. **No contract does this any more.**
4. The maker builds its claim transaction, spending the coin and a reserved L-BTC fee coin. It sends the transaction and its nonce.
5. The taker checks the transaction spends the coin, and replies with its nonce and adapter share for `T`.
6. The maker verifies the share, combines it with its own, checks the result against the output key, and **stores it durably**.
7. Only then does the maker lock on Solana, to `T`.
8. The taker checks the escrow and claims, revealing `s`.
9. The maker computes `t`, completes the signature and publishes its claim.

Refund: the taker after `lock_height`, the maker after `deadline_slot`, as today.

### SOL-USDT → L-USDt

1. RFQ, as above, with the taker's receiving script.
2. The taker locks on Solana, to `T`.
3. The maker checks the escrow, then funds the confidential address and a blinded L-BTC fee coin for the taker.
4. The taker unblinds and checks the coin, builds its claim transaction, and sends the transaction and its nonce.
5. The maker checks it spends the coin, and replies with its nonce.
6. The taker sends its adapter share.
7. The maker verifies it, combines with its own share, checks the result, and **stores it durably**. Then it sends its own share.
8. The taker completes the signature with `t` and publishes.
9. The maker extracts `t` from the published signature, computes `s`, and claims on Solana.

**The order in steps 6 and 7 is what keeps the maker safe.** If the maker sent its share first, the taker could claim on Liquid with
`t` while the maker, lacking the adapter signature, could never extract `t` to collect on Solana.

## New risks, compared to the HTLC

| Risk | Handling |
|---|---|
| No on-chain check of asset or amount | Each party unblinds and checks before acting. A bug here loses money, where the covenant would have refused. |
| **Nonce reuse leaks a key** | Nonces are fresh randomness, held in memory and used once. A crash abandons the session. They are never stored, and the type consumes the nonce on signing. |
| A claim transaction is fixed in advance | A signature commits to all inputs, so a fee coin spent elsewhere kills an adapter signature, and a new one needs the counterparty. Fee coins are reserved per swap. |
| Signing needs both parties online after funding | Nostr now matters mid-swap. An outage before signing only delays, because refunds need nothing but the chain. |
| The adapter signature is critical state | Stored durably before anything depends on it. Losing it after locking on Solana loses the claim. |
| Less-vetted crypto | `musig2` 0.4.1's adaptor code has no audit we could find. |
| Simplicity's role shrinks | Formal verification now covers only the refund leaf, while the claim rests on MuSig2 and adaptor security. |

## Wallets must be confidential too

If a funding transaction spends explicit coins, anyone can read the input value and bound the blinded output, so **the signer's wallet
holds only blinded coins, and all its change is blinded.** The L-BTC fee output is the one explicit output, because Elements requires it.

Each maker claim uses its own fee coin, made just before signing, because the adapter signature commits to it. A fee coin costs one
extra transaction per swap.

## Stage 1: proving it

All done, on real systems:

| Check | Result | Where |
|---|---|---|
| Blinded funding from a wallet, unblinding, adapter-signed claim and secret extraction | Mined by Elements 23.3.4 under default relay policy: 1,376 vB, one 65-byte witness item, hidden output, neither `t` nor `T` in the transaction | `contracts/swapkey/tests/regtest.rs` |
| Simplicity refund leaf: key, lock height and sequence rules | Refused and accepted correctly. A refund shows 4 witness items, so it is recognisable. | Same test |
| `recover` point check in the compiled program | Opens only with the right value, including sign and range edges. A claim costs 40,916 CU. | `programs/solana-escrow/tests/escrow.rs` |
| The same values, computed separately from the curve's definition | Match the Rust code and the program | `contracts/swapkey/tests/values.rs` |
| Blinding, proofs and adapter signing in a browser | Headless Chromium 145 built and signed a whole claim in 414 ms, with a 4.9 MB module. The node accepted it at a 300-sat fee. | `scripts/check-browser-claim.py` |

Not yet covered: the program on a public cluster with this change, Firefox and Safari, and a real wallet paying a confidential address of this form.
